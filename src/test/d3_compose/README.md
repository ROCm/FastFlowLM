# d3 compose test

`test_d3_compose` checks FastFlowLM's port of the d3-turbo composed requests (`src/common/decision/d3_compose.cpp`,
`d3_composed.cpp`: `assets`, Box questions, the 128-bin readout) against the upstream package it reproduces
(`vllm-sr/d3-turbo` v1.1: `d3_compose.py`, `d3_format.py`, `d3_runtime.py`). No NPU and no model weights are involved.

```bash
cmake -S src/test/d3_compose -B build-d3-compose && cmake --build build-d3-compose
ctest --test-dir build-d3-compose --output-on-failure
```

What it requires:

- **units** (`compose_units.jsonl`): `check_references`, `split_string`, `describe_parts` (JSON whole-value
  references, stray sentinel characters), `hoist_state`, `user_parts` + the rendered chat text (byte identical, with
  front images, videos, images inside instructions / options), the Box tail and edge-marker suffix, `format_seconds`,
  `round(t, 3)`, `window_plan` / `group_times`, and the math on synthetic distributions: `expected`, `order_edges`,
  `decode`, the 512-point R4 confidence (numpy pairwise sums, `searchsorted`, exact cdf ties), `calibrate`
  (`decision_config.json systemone.box_calibration`) -- all bit for bit.
- **offsets** (`compose_offsets.jsonl`): the readout positions (box 9, 6, 3, 0; track 12, 9, 6, 3, 0) from token ids and
  token byte lengths equal upstream's offsets-mapping result, including the two error cases of A11.
- **requests** (`compose_requests.jsonl`): whole composed requests run through the package's own
  `D3._system_one_composed` with a stand-in encoder (seeded random hidden rows, random readout). Per row: the same
  prompt bytes, token ids (crc), state block length, readout plan; then the same response *exactly* from upstream's own
  probabilities (inline errors with reasons, box / confidence, usage), and from the recorded hidden rows through the
  scripted CPU engine and the fp32 readout on the C++ side (numbers within the float noise of the readout; the
  engine request is checked too: one call per state, readout positions, images deduplicated).
- hand-written cases: request-level 422 texts, routing, refusals, the engine interface (duplicates, shared option
  images, bad own images, flags, length limit, track), and the d3_contract fuzz corpus pushed through the composed
  path (only `RequestError` may escape).

Fixtures are generated by `gen_compose_fixtures.py` with the upstream Python (transformers, torch, numpy and pillow; CPU is enough):

```bash
python gen_compose_fixtures.py --package <vllm-sr/d3-turbo dir> --out fixtures --seed 5 --units 3000 --requests 300 --offsets 500
```

The committed `fixtures/` are a compact subset of that output (every 5th request / offsets record and every 5th unit of
each frequent kind: 60 requests, 100 offsets, 1,178 units, 3 MB instead of 14 MB), made with

```bash
python subset_fixtures.py <full fixtures dir> fixtures --every 5
```

The full set (300 requests, 500 offsets, 5,806 units) is not committed. Generate it into a scratch directory with the
command above (`--out /tmp/compose-full`) and run the tests against it:

```bash
cmake -S src/test/d3_compose -B build-d3-compose -DFLM_D3_COMPOSE_FIXTURES=/tmp/compose-full
```

Regenerating the committed fixtures is a reviewed change: the fixtures are the definition of "identical to upstream".

## Options

- `-DFLM_D3_TEST_TOKENIZER=ON -DFLM_D3_TURBO_PACKAGE=<D3-Turbo-NPU2 dir>` builds `test_d3_compose_tokenizer`: the same
  fixtures with FastFlowLM's own `Tokenizer` (ids and token byte lengths) instead of the recorded ids. Prompts with
  combining marks (Thai, Devanagari) are skipped: transformers' `Qwen2Tokenizer` and `tokenizer.json` split those
  differently (pre-existing, as for the smaller d3 models).
- `-DFLM_D3_TEST_ADAPTER=ON` builds `test_d3_adapter`: the engine adapter's routing by capability bits, the
  `d3_state_request` it builds (question-image table, video pads as `video_token_id` or rewritten) and the per-row path
  against a mock `decision_model` (needs the device runtime headers). The call into the real library
  (`d3_npu::encode_state_once`) is only compile-checked.
- `test_d3_video_composed` (always built; needs only the fixtures' `decision_config.json`): M4 of the composed requests
  through the scripted engine, with a fake window source: a track at rate 2 (one state-once call per window, the
  moments as blocks with five readout rows, video pad runs, the window's pixels, usage, release of the pixels), a box at
  a moment (nearest moment, `time`), the question shapes and refusals of `_video_box`, the row budget (A5), unreadable
  clips, a request with a state image + plain video question + box + track, and `load_video_windows` over a fake decoder.
- `D3_TEST_MAXFAIL=<n>` prints more than the first 60 failures.
