Q4_K on the NPU

01

The problem the re-fit solves

Q4_K's metadata is built for a CPU: an fp16 super-block scale multiplied by a 6-bit per-group integer. The AIE vector unit has no fp16 multiplier worth using — its native high-throughput operand is bf16, with an 8-bit significand. Rounding Q4_K's fp16 S straight to bf16 throws away three mantissa bits of a value that every one of 256 weights depends on.

The converter's answer is not to round S and keep sj. It is to observe that the kernel only ever uses the product tj = S·sj, then re-derive a fresh pair (bf16 S′, uint8 s′j) against that product. The two extra bits gained by going uint6 → uint8 are spent absorbing S′'s rounding error rather than as a plain ×4 — which would be a no-op, since S/4 has exactly S's significand.

The whole pipeline in one line Read the GGUF block → factor out tj, uj exactly in fp32 → apply model reorders → re-fit each side onto (bf16, uint8) per 256 columns → transpose into the kernel's column-major chunk.

Unpacking the 6-bit fields

The 12 scale bytes are not eight tidy 6-bit fields. Groups 0–3 take a plain 6-bit field from the first four bytes; groups 4–7 take a low nibble from the last four bytes plus two high bits borrowed from the first four. This is llama.cpp's get_scale_min_k4, vectorized:

# lo = scales[0:4]   hi = scales[4:8]   top = scales[8:12]
s6 = concat[ lo & 0x3F,                                # j = 0..3
             (top & 0x0F) | ((lo >> 6) << 4) ]          # j = 4..7
m6 = concat[ hi & 0x3F,                                # j = 0..3
             (top >> 4)   | ((hi >> 6) << 4) ]          # j = 4..7

Factoring, not re-quantizing

What comes back out of the unpacker is not the Q4_K structure. It is the collapsed product, one pair per group of 32:

unpack_q4_k returns tj = S · sj   and   uj = M · mj   — both float32, both exact
so that   wji = tj·qji − uj

Exact is the operative word: an 11-bit fp16 significand times a 6-bit integer needs 17 bits, and fp32 carries 24. Nothing is lost, nothing is re-quantized, and no super-block structure survives this step.

Why that matters The result has the same shape and the same 32-column granularity as unpack_q4_1's (d, m, qw), so it can pass through every model-specific row/column reorder untouched. Some of those reorders move chunks finer than 256 columns — ssm_out_proj moves 128-column chunks — which would leave a super-block's metadata unrepresentable if it had been fixed here. The re-fit is deliberately deferred until after the reorders, inside _pack_q4k, so it always fits the 8 groups that genuinely end up sharing a super-block.

There is a second reason the direct path exists. The obvious alternative — dequantize Q4_K to bf16, then re-encode as Q4_1 — costs 0.240 bits of ENOB and 0.375 bpw against reading it natively, and damages the distribution tail far more than the mean. Q4_K therefore gets a dedicated branch rather than the generic dequantize/requantize fallback that q5 and q6 still take.

03

The re-fit: (uint6, fp16) → (uint8, bf16)

_refit_one_side runs once per side per super-block. Given the 8 exact tj, it produces one bf16-representable P′ and 8 integers p′j ∈ [0, 255] with P′·p′j ≈ tj. Four decisions carry the whole method:

1 — The sign rides on P′

p′j is unsigned, so the sign is pulled out of the largest-magnitude entry and folded into P′. Q4_K's d and dmin are non-negative, so every tj in a group already shares one sign.

2 — P′ is rounded away from zero

_to_bf16_up rounds the magnitude of max|tj| / 255 up to a bf16 value. Rounding up is what makes overflow structurally impossible: with a slightly-too-large P′, the quotient tj/P′ can never exceed the 255 cap.

3 — p′j is re-derived against the rounded P′

This is where the two extra bits get spent. P′ is fixed first; only then is each p′j = clip(round(tj/P′), 0, 255) computed. Since the quotient runs up to 255, it can absorb up to 255·2−8 ≈ 1 integer step of P′'s rounding error — and the uint8 grid, four times finer than the uint6 grid it came from, can represent exactly that.

4 — A small search over P′ candidates

The smallest admissible P′ is not always the best one. A slightly larger P′ often aligns with several tj at once. The code scores search + 1 consecutive bf16 values starting at the base and keeps whichever minimizes Σj (P′p′j − tj)². search = 3 is the knee of the measured sweep; it is also what removes the re-fit's sensitivity to how spread the tj are.

base = to_bf16_up(max|t| / 255)              # rounded away from zero
for c in 0..search:
    P_c = bf16_next_up(base, c)               # c-th bf16 value above base
    p_c = clip(rint(t / P_c), 0, 255)
    err = sum((P_c * p_c - t)**2)              # scored in float64
    keep the (P_c, p_c) with the smallest err

Both sides go through the same routine — S′, s′j from tj and M′, m′j from uj — and then one small semantic fix is applied at pack time: GGUF subtracts the min, while the kernel adds both accumulators, so M′ is stored negated.

04

The packed block

One q4k_block_t covers a 32 × 256 chunk — QXNX_ROW_BLOCK_SIZE rows by QXNX_COL_BLOCK_SIZE columns — laid out column-major over the chunk. Because aie_array_layout.h pins PARALLEL_ROWS = QXNX_ROW_BLOCK_SIZE for __Q4_K__, a column is the whole row block: Q4_K is the one format the layer never strides, and the cores take a single pass.

kernels/model_spec.h
typedef struct {
    uint8 scales[ROW_BLOCK * COL_BLOCK / GGML_GROUP_SIZE];  // s'_j
    uint8 mins  [ROW_BLOCK * COL_BLOCK / GGML_GROUP_SIZE];  // m'_j
    uint4 qs    [ROW_BLOCK * COL_BLOCK / 2];
    bf16  S     [ROW_BLOCK * COL_BLOCK / 256];
    bf16  M     [ROW_BLOCK * COL_BLOCK / 256];             // stored negated
} q4k_block_t;

Within qs, one column is 32 nibbles — the whole row block — with rows paired into a byte, the even row in the low nibble, and columns ascending. Because a 256-column chunk holds exactly one super-block, S and M reduce to a single 32-wide bf16 vector each, and the kernel needs no super-block loop at all.

05

Reduce first, scale after

The kernel evaluates y += W·x in a shape chosen so the scalar metadata meets the data as late as possible:

what the kernel computes w = S′·s′j·q  +  M′·m′j
y = S′ · Σj s′j(Σi qixi)  +  M′ · Σj m′j(Σi xi)

The whole 32-value group is reduced against x in one float32 accumulator, and only then meets s′j. S′ is applied once per super-block. The min path never needs the quants at all — it only needs Σi xi per group, which is the same for every row and is computed once per mvm() call.

Before the code, the shape. One super-block is 8 groups of 32 columns, and the reduce happens in three levels — each one folding a wider span of data into fewer numbers:

The inner load shape

One 512-bit uint4 load pulls 128 nibbles. At PARALLEL_ROWS = 32 that is 4 whole columns, so a 32-column group takes 8 loads. Each load is widened to bf16 — exact, since uint4 ⊂ bf16 — and then split into 4 row-vectors, each MAC'd against one bf16 scalar from the activation vector. A 32-wide MAC already covers the accumulator dependency, so a single temp_acc suffices; there is nothing to interleave against.

for g in 0..8:                          // groups per super-block
  b_col = load_v<32>(x)
  temp_acc = 0
  for l in 0..8:                        // 8 loads of 128 nibbles
    q_bf16 = to_float(load_v<128>(qs))  // uint4 → bf16, exact
    for k in 0..4:                      // 4 columns per load
      temp_acc = mac(temp_acc, q_bf16.extract<32>(k), b_col.get(4*l+k))
  acc_s = mac_f32_bf16_low(acc_s, temp_acc, s′)
  acc_m = mac(mac(acc_m, m′, lo), m′, hi)
06

Where the rounding is allowed to land

Every multiplier operand in this datapath is bf16-exact by construction. q is a uint4; s′ and m′ are uint8, and bf16 holds every integer up to 256; S′ and M′ were stored as bf16. A rounding can therefore only ever land on an accumulator — and the design's whole numerical argument is about which of those accumulators are allowed to round.

The cancellation ratio The scale path and the min path are large and opposite; y is the small difference between them. Measured RMS over real layers: the scale path runs 13.1 against a 5.67 output (2.32×) and 36.6 against 15.9 (2.30×). Any relative error introduced before that cancellation is amplified ~2.3×, and it does not average away over the K loop — it is measured against the small number. The one rounding that sits after the cancellation, the final bf16 on y, comes in at 1.0×. The roundings to attack are the ones inside the group, not the ones at the end.

Three accumulators reach the output, and none of them is rounded to bf16 on its way in. Each goes through a two-limb split instead — split_f32 writes x ≈ l₀ + l₁ as two bf16 values, and each residual is exact in fp32 because l₀ is within a factor of two of x:

The three splits, and what each costs

The group sum. Rounding temp_acc to bf16 before it meets s′j would be the single largest error the kernel can introduce: 2e−03 relative, taken once per group, correlated across the 8 groups that share an S′, and then amplified 2.3×. The split costs 1 extra MAC per group against the 32 MACs of the loop that produced the sum.

The two super-block accumulators. Same reasoning one level up, and twice. The split costs 2 extra MACs and 2 msc per 32×256 block — amortized over roughly 800 vector ops, and landing in the loop's drain phase.

The activation column reduce. aie::reduce_add over a bf16 vector already sums in accfloat, but it returns bf16 and discards 16 mantissa bits. That error would ride the entire min path and then meet the cancellation. So mvm() reduces in float32 and hands the kernel two bf16 limbs, smallest first, so the small term joins acc_m before it meets the large one. This runs only when i == 0 and is read back by every row block, so in the steady state the split is free.

Emulated against an exact float64 reference — npu_q4k_emulate.py whole datapath vs. exact  ≈  1e−05 relative
the Q4_K format itself  ≈  4e−03 relative   — two orders of magnitude apart

That gap is the point of the exercise. The arithmetic is far enough below the quantization floor that the kernel is not what limits accuracy — the format is.

07

How the loop is driven

mvm() in proj_main.cc walks output row blocks on the outside and K blocks on the inside. For Q4_K it never zeroes y_acc: the accumulator pair is declared in registers, zeroed by _Q4K_zero, carried across the whole K loop, and collapsed by _Q4K_finalize only once the row is complete.

for i in 0 .. M/32:
    _Q4K_zero(c_accum_s, c_accum_m)            // registers, not y_acc
    for j in 0 .. K/256:
        acquire x, acquire w                    // ping/pong double buffers
        if i == 0: fill b_col_reduce_add[j]      // Σx per group, 2 bf16 limbs
        _Q4K_x_bf16(c_accum_s, c_accum_m, x, w, b_col_reduce_add + …)
        release w, release x
    _Q4K_finalize(y_acc, c_accum_s, c_accum_m)
    copy_float_to_bf16<32>(y_out, y_acc)

The i == 0 guard is the one piece of state that crosses row blocks. Σi xi depends only on the activations, which are identical for every output row, so the reduce runs on the first row block and every subsequent one reads it back. The buffer is sized 2 * INTERMEDIATE_SIZE / GGML_GROUP_SIZE — two bf16 limbs per group across the widest K any phase will present.

Everything else is the standard FLM projection loop: five mvm() calls per layer for QKV, O, up/gate and down, ping-pong locks on x and w, and a packet id written ahead of the output so the result routes to RoPE, the GLU, or the residual add.

08

The three datapaths, measured

Two harnesses, two questions. enob_flm_vs_llamacpp.py models the computation graphs element for element against ports of llama.cpp's own reference encoders, and answers how good is the format plus its datapath. npu_q4k_emulate.py runs the real kernel's arithmetic over a real GGUF tensor, and answers how much does the datapath add on top of the format.

Two error terms are reported and then composed in quadrature as ENOB* = −log₂ ε:

definitions εW = ‖Weff − w‖ / ‖w‖   — the format: what an exact accumulator would have multiplied
εpath = ‖y − Weffx‖ / ‖wx‖   — the datapath, paired against its own effective weights

The format decides everything; the datapath decides almost nothing. εW ≈ 7·10⁻² against datapath terms of ~5·10⁻³ — in quadrature that moves the total by 0.004 bits. On gaussian activations the two vendors land within 0.001 bits of each other, having paid in opposite places: llama.cpp buys exact integer MACs with 2-bit-worse activations, FLM keeps BF16 activations and pays roundings later.

The tie breaks on real activations Gaussian x is the best case for a block int8 quantizer. With 1% of values at 8× — what LLM activation channels actually look like — Q8_K's single scale across 256 values coarsens the whole super-block and llama.cpp loses 1.42 bits of ENOBpath (7.151 → 5.733), for ENOB* 3.803 → 3.761. BF16 is scale-free, so FK is flat at 3.804.

The real kernel on a real tensor

npu_q4k_emulate.py, qwen3.5-4b-q4k.gguf, 512 rows, 4 trials. Here the datapath is measured against an exact matmul over the same re-fitted weights, so the format cancels out entirely and only the arithmetic is left:

That second row is the number quoted in q4_core.h's header comment, and it is the whole argument for the two-limb splits. The datapath contributes 1e−05 against a 3.4e−03 format — its quadrature contribution to ENOB is under 10−4 bits. Every rounding that mattered was one that landed before the min subtraction, where the cancellation charges 2.3× its nominal price; the limbs move all of them after it.

Reading the harnesses Both scripts carry rows that no longer describe the shipping kernel. npu_q4k_emulate.py defaults to group_limb=False, reduce_limb=False, which models an earlier datapath, not the one in today's q4_core.h and proj_main.cc. And enob_flm_vs_llamacpp.py splits only the two super-block accumulators, leaving bf16 casts on the group sum and on Σx — so the 5.412e−03 in the table above is an upper bound on the real datapath, and the 1.010e−05 measured on a real tensor is the honest figure.
