gated_attention_verify — Dataflow & Layout

One full-attention (softmax) layer of Qwen3.8-27B on an AMD npu2 8×6 AIE2 array, built with IRON. Generated from the source in this folder: iron/, kernels/, host/, models/.

0 · At a glance

what it is
A single decoder layer — every 4th layer of Qwen3.8-27B (the other three in four are gated delta-net and live in ../gate_delta_net_verify, a separate xclbin). There is no phase select anywhere in this design.
math
h1 = x + o_proj( attn(q,k,v) ⊙ σ(z) )
h2 = h1 + down_proj( silu(gate) · up )
batch
L_TOKENS = 8 query rows per forward pass, threaded from the Makefile into IRON (env var), the kernels (-DL_TOKENS) and the host (-DL_TOKENS).
weights
Q4_K, 4.625 bits/weight, 32×256 blocks. 372,244,480 weights per layer → 205.2 MiB in DDR.
activations
bf16 everywhere on the array; fp32 accumulators inside the kernels.
tiles used
16 MVM cores + 7 special cores + 2 coreless residual tiles + 6 memtiles + 6 shims.
DDR round trips
Exactly two sinks: the appended K|V cache (IT[4]) and h2 (IT[3]). Everything else stays on the array.
Status. Per iron/layer_aie.py and README.md: the attention datapath itself — iron/attn.py's shapes and the mask in kernels/attn_qk.cc — is still L = 1 shaped, and this design has never been on hardware. Everything outside the mixer (projection engine, x replay, rms/residual) is shared tile-for-tile with the delta-net project. See §15 for the specific gaps.

1 · Scope & status

This project is a verification build: host/host.cpp runs a bit-accurate CPU golden model of layer 3 (constexpr int kAttentionLayer = 3;) alongside the NPU and compares. The CPU reference calls round_bf16() at every point the array narrows a value, so the comparison is meaningful down to the last ulp rather than a loose cosine threshold.

2.3 The five matrix-vector products

Every projection is y[M] = W[M,K] · x[K] replicated over L_TOKENS rows. rounds = M / M_PER_ROUND is the number of x replays the engine consumes, and blocks = (M/32)·(K/256) is the Q4_K block count.

4.1 Column occupancy, in words

ColContents
0, 1, 6, 7The 16-core projection engine: 16 proj_main cores, 4 memtiles, 4 weight shims. Columns 0/1 form one y-assembly group (rooted at MT[0]); columns 6/7 form the other (rooted at MT[6]).
2MT[2], the x replay for all four projection phases, and CT[1][2], the SwiGLU. CT[0][2] lends the rms tile half of its resident residual (h4..h7) as pure addressable memory and therefore must stay coreless; CT[2][2] and CT[3][2] are free.

5Entirely free — no compute tile, no memtile, no shim in use. It was the conv / a-b column in the delta-net design and held the SwiGLU here until the GLU moved to CT[1][2]; it is kept clear so attention can grow into columns 4 and 5.

4.2 Why the residual sits where it does

The rms core is at CT[0][3] = physical (row 2, col 3). An AIE2 core can address four memory windows (AIE2TargetModel::isLegalMemAffinity):

0x400000x500000x600000x70000
south — compute rows only (row ≥ 3) westnorthown

At row 2 the tile to the south is a memtile, so south is unusable. That leaves west = CT[0][2] and north = CT[1][3] — exactly the two tiles rms_residual.py is handed as residual_tiles. Each holds rows_per_tile = 4 resident hidden rows of D = 5120 bf16 = 10 KiB, so 40 KiB of each tile's 64 KiB. Neither tile has a core or a mem block: the rms core loads and stores through the neighbour window directly, so the residual never touches a DMA, a lock, or DDR.

4.3 Why the SwiGLU sits in column 2

The GLU tile is the most mobile IP in the design: four round buffers of its own, no neighbour memory, one producer and one consumer. Both of those are already next to column 2 — up|gate arrives off MT[1]'s y port one column west, and the result goes to MT[2]'s dedicated down replay buffer in the same column. Putting it on CT[1][2] makes both legs local:

MT[1] ──east──▶ (col 2, row 1) ──north──▶ (col 2, row 2) ──north──▶ CT[1][2]   up|gate, pkt to_glu
CT[1][2] ──south──▶ (col 2, row 2) ──south──▶ MT[2]                            hid, pkt to_down_proj

Only CT[0][2] is off limits — it carries the rms tile's resident h4..h7 and must stay coreless (§4.2) — so CT[1][2] is the closest legal tile. CT[2][2] and CT[3][2] stay free.

What this buys. Column 5 is now completely empty. Attention is the one part of the layer that does not fit its column — two CUs on four compute tiles, one memtile for both the KV cache and the o reassembly — so column 5 is held clear as the room it grows into.
The move adds one rule split to the y tree: at column 2's memtile switchbox to_glu = 16 turns north while to_rope | to_aux | to_rms = 4 | 8 | 2 carry on east. Bit 4 separates the two groups cleanly, which is the whole reason the ids are one-hot (§14.1).

5 · End-to-end dataflow

The wiring below is layer_aie.py's 17 connect_port calls plus the three route() helpers, in the order the layer executes them. Connection order in the source is deliberate — long routes are declared first so the pathfinder places them before the short ones compete for switchbox ports.

  1. input_layernorm — rms phase 1

    IT[3].MM2S0 --pkt to_rms(0)--> rms_core.X_in (x, L×D rows) IT[3].MM2S1 --pkt to_rms(0)--> rms_core.W_in (2×D norm weights) IT[3].MM2S0 --pkt to_rope(1)--> rope_core.ROPE_in (cos/sin + q/k norm weights)

    One shim channel carries two different streams north into column 3 — the layer input and the RoPE table — told apart by packet id. That is one destination set with two masksets. Channel 1 carries the norm weights and reuses to_rms, because it lands on a different S2MM channel of the same tile and therefore never needs the id to disambiguate.

    The rms core runs rms_residual() in an infinite loop. Phase 1 takes a fresh x row, computes RMSNorm with rms_weights[0:D], stashes the raw x row into the resident h buffer for the later residual add, writes packet id rms_pkt_id.to_proj = 0 into y[14], and hands the row to its MM2S.

  2. x replay staging

    rms_core.Y_out --pkt to_proj(0)--> x_replay_mt.x_in(0) [MT[2] S2MM0, "main" buffer] x_replay_mt.route_to(proj_engine.X_in) [MT[2] MM2S* --> MT[1] S2MM3] proj_engine.route_x() [MT[1] MM2S4 --> 16× CT.S2MM0, circuit]

    MT[2] lands the whole L×D activation (80 KiB) and then replays it once per engine round — 28 times for qkv|z. Each replay walks the buffer in column-block-major order ([(D/256,256),(L,D),(256,1)]) so each of the K/256 = 20 emissions is exactly one x_slice_ty = L×256 = 2048 bf16.

    The replay hops one column west into MT[1], whose two-slice FIFO is the design's only source of x. From there a single circuit-switched flow broadcasts to all 16 cores, so no core needs a mask/match rule. See §7 for why the FIFO cannot live on MT[2] itself.

  3. fused qkv | z projection

    proj_engine.route() IT[0,1,6,7].MM2S0/1 --> MT[0,1,6,7].S2MM4/5 (Q4_K weights) MT[i].MM2S[j] --> CT[j][col_i].S2MM1 CT y --> MT[0]/MT[6] --> MT[1] (y tree, replicated per pkt id) proj_engine.Y_out --pkt to_rope(4)--> rope_core.QKV_in proj_engine.Y_out --pkt to_aux(8)---> aux_mt.Z_in

    Two mvm() calls off one resident x: the fused qkv (M = 8192, 16 rounds) and the output gate z (M = 6144, 12 rounds). They are separate calls but share the same 28-replay x phase, which is why QKV_REPEATS sums both.

    Every round produces M_PER_ROUND = 512 output rows × L tokens = 4096 bf16, assembled in MT[1] as m_full_ty = (16·256 + 2,) = (4098,) — 16 core contributions of L·32 = 256 values each, plus a 2-element packet header the kernel wrote at y[14].

  4. q/k norm + partial RoPE — CT[3][3]

    rope_core.Q_out --pkt 0--> attn CU0.Q_in (q_buffer[0 : DQ/2]) rope_core.Q_out --pkt 1--> attn CU1.Q_in (q_buffer[DQ/2 : DQ ]) rope_core.KV_out --------> IT[4].S2MM0 (k then v, alternating)

    The RoPE tile's inbound BD chain on S2MM0 alternates kv_in_buffer then q_in_buffer. That ordering is why the host writes weights as k, v, q rather than q, k, v (see §13).

    Per invocation the core: RMSNorms each 256-dim q head with rope_buffer[ROPE_DIM ..] and each k head with rope_buffer[ROPE_DIM+DH ..], rotates only dims [0, 64) of both using rotate-half (halves 0..31 / 32..63) against the cos/sin in rope_buffer[0:64], copies dims [64, 256) through unchanged, and leaves v untouched.

    Q_out is a packet flow with one leg per CU: the two CUs hold different kv heads, so each takes the q heads of its own GQA groups and the id selects between them. The MM2S chain uses an extra lock (q_pass_lock, id 10, init 0) so that BD 0 (pkt 0) always precedes BD 1 (pkt 1) within a token.

  5. KV cache round trip through DDR

    This is one of only two DDR sinks. KV_out emits k (1024) then v (1024) alternating, so the shim sees an interleaved k0 v0 k1 v1 … stream. A single 4-dim S2MM BD on IT[4] de-interleaves it straight into the two halves of the cache:

    sizes   = { L_TOKENS,  2,        data_per_chunk/1024, 1024 }
strides = { data_per_chunk, v_offset, 1024,           1    }
offset  = (L - L_TOKENS) * data_per_chunk        // append point

    The host then reads the whole cache back on IT[4]'s two MM2S channels as two linear transfers — k from offset 0, v from kv_cache_size/2, each L_padded · DH · num_kv_heads long — and MT[4] fans them out to the CUs. All the reads are posted before any weight moves (§13.3).

  6. GQA softmax attention — column 4

    _attn_column.route() IT[4].MM2S0/1 --> MT[4].S2MM0/1 (k, v) MT[4].MM2S0/1 --> CU0/CU1 qk .K_in MT[4].MM2S2/3 --> CU0/CU1 kv .V_in CU0/CU1 .O_out --> MT[4].S2MM2/3 (o halves) MT[4].MM2S4 --> (pkt 0) gate tile

    Each CU is a vertical pair: attn_qk below, attn_kv above. They communicate through shared score buffers — s_buffer_0/1 of type (NQ_PER_CU·16 + 16, 1) = (144, 1) — allocated on the kv tile and reached by the qk core through its north window, so the scores never enter a DMA. See §8.

  7. sigmoid output gate — CT[2][3]

    aux_mt.Gate_out ---------------> gate_core.Gate_In (z, token-major, L BDs) _attn_column.O_out --pkt 0-----> gate_core.Attn_In (attn, token-major)

    z is the engine's second mvm off the same resident x, so nothing new is needed on the way in — only somewhere for it to wait. MT[3] parks the whole L×DQ activation (96 KiB) and de-permutes it out of row-block order in the inbound BD, so the gate tile sees token-major rows and stays at one row per invocation.

    The attention output needs no staging: MT[4] hands it over token-major and it is the last operand to arrive anyway.

    The kernel computes gated[i] = attn[i] · sigmoid(z[i]) over all DQ = 6144 lanes and stamps aux_to_proj_x_in_pkt_id.to_out_proj = 2 on the way out.

  8. o_proj

    gate_core.Attn_Out --pkt to_out_proj(2)--> x_replay_mt.x_in(1) [MT[2], phase "o"]

    The gated rows re-enter MT[2] on the same inbound port as qkv|z's x, told apart by arrival order; the id exists only for the rms leg that shares the port. Phase "o" has x_dim = DQ = 6144 and 10 replays, each emitting 24 slices of 2048.

  9. residual add + post_attention_layernorm — rms phase 2

    proj_engine.Y_out --pkt to_rms(2)-------> aux_mt.OProj_in [MT[3] S2MM2] aux_mt.Residual_out --pkt to_residual(3)-> rms_core.X_in [one hop north]

    o's y leaves MT[1] east, drops off at MT[3], is un-permuted by the inbound BD ([(D/32,32),(L,D),(32,1)]), and hops one tile north into the rms tile's X port — a merge with the shim's phase-1 rows, ordered purely by the layer's data dependencies.

    The rms core reads h[t] out of the neighbour window, computes h1 = bf16(x_in + o_proj), writes h1 back into h[t] for the second residual, normalises with rms_weights[D:2D], and stamps rms_pkt_id.to_st = 1.

    Neither residual operand touches DDR. The old L = 1 design bounced o off IT[1] and read it back, because nothing on that path could transpose. Here the un-permute is free — it is just the shape of MT[3]'s landing BD.

  10. up|gate projection + SwiGLU — CT[1][2]

    rms_core.Y_out --pkt to_st(1)---------> x_replay_mt.x_in(2) [MT[2], phase "up_gate"] proj_engine.Y_out --pkt to_glu(16)----> glu.Up_Gate_in [CT[1][2]]

    x_in(2) is physically the same MT[2] port that to_proj already reaches, but it gets its own connect_port because rms_residual.cc stamps the id per phase — this row travels under to_st.

    The host weaves the up and gate weight matrices in blocks of WEAVE = 512 rows (= M_PER_ROUND), so the engine's 68 rounds arrive as up₀ gate₀ up₁ gate₁ …. The GLU tile therefore only ever needs four round buffers of L·512 = 4096 bf16 (32 KB total, half the tile): it consumes pairs = I/512 = 34 pairs, emitting silu(gate)·up for 512×L values at a time.

    x_prod_lock is initialised to 2, not 1: the kernel holds both inputs of a pair.

  11. down_proj

    glu.Hid_out --pkt to_down_proj(19)--> x_replay_mt.x_in(3) [MT[2], "down", dedicated buffer] proj_engine.Y_out --pkt to_rms(2)---> aux_mt.OProj_in

    down is the one phase with dedicated = True: its 272 KiB staging buffer is separate from the 96 KiB shared one, so it can fill while up|gate is still replaying. It is also the one phase with in_block = 32, because the GLU emits row blocks rather than token-major rows — see §9.3.

    At L = 8 the whole hid is L·I·2 = 278 KB, far more than a compute tile holds. That is why feeding down means a third replay spec on MT[2] and not, as at L = 1, simply restoring an old lock init on the GLU tile.

  12. h2 to DDR — rms phase 3

    rms_core.Y_out --pkt to_out(4)--> IT[3].S2MM1 --> DDR @ layer_out_offset

    Phase 3 takes no norm weight (the S2MM1 weight chain fires only twice per invocation) and applies no normalisation. It reads h[t] = h1 from the neighbour window, adds down_proj, and ships h2 south. The host's landing BD is {L_TOKENS,1,D/1024,1024} / {D,0,1024,1} at layer_out_offset = L_TOKENS·D, on bd_9, IT[3] S2MM ch1 — the transfer the host finally waits on.

6.2 Inside one combo

proj_combo makes cts[0] the main core: it owns the two y buffers (y_0, y_1) and has send_x_out = True, i.e. the MM2S that ships them. cts[1] is the partner: it has no MM2S at all and writes its half of the result directly into the main core's buffer at offset 16 + L·m through the neighbour window, guarded by _down_lock_* operations on the main core's locks.

The partner still allocates two unused buffers named _y_0 / _y_1 — purely so that the RTP/buffer address layout of the two cores matches, since both run the same proj_main.o.

Reconstruction is w = S'·s'j·q + M'·m'j, evaluated as “reduce first, scale after”: the per-group integer sums are accumulated and only then multiplied by the bf16 super-block scale, which keeps the min/scale cancellation from amplifying rounding. Two-limb bf16 splitting (bf16_limb::mac_f32_bf16_low) is used where the cancellation is worst.

Two variants:

  • _Q4K_x_bf16 — single row, all accumulators in registers.
  • _Q4K_x_bf16_L<L> — L rows. AIE2 has only four 1024-bit AM registers, so accumulators spill to memory. Compensating optimisations: nibbles are unpacked once per group into q_scratch and re-read by all L rows, and the min path is hoisted out of the group loop. Helpers _Q4K_zero_L and _Q4K_finalize_L (c = c_accum_s + c_accum_m) bracket it.

Constants: SUPER_BLOCK_SIZE 256, GROUPS_PER_SB 8, NIBBLES_PER_LOAD 128, COLS_PER_LOAD 4, LOADS_PER_GROUP 8.

The 63-count lock ceiling → fanout

A memtile lock counter is 6 bits, so no single lock op may exceed 63. up_gate needs 68 replays. _pick_fanout is gcd-based: for the shared 5120-wide channel, gcd(28, 68) = 4; the smallest divisor f of 4 with max/f ≤ 63 is f = 2. So that channel gets two cons locks and the credits become qkvz: 28/2 = 14, up_gate: 68/2 = 34. Only the last BD of a fanout cycle credits the producer.

The credit ledger is a closed ring

7.4 BD shapes

Landing BD

if in_block == 0:                       # token-major arrival (qkvz, o, up_gate)
    linear, len = L_TOKENS * x_dim

else:                                   # row-block arrival (down)
    blocks   = x_dim // in_block                       # 17408/32 = 544
    hi, lo   = _split_bd_size(blocks)                  # 544 > BD_MAX_SIZE(512) -> (2, 272)
    dims     = [(hi, lo*in_block), (lo, in_block)] + [(L_TOKENS, x_dim), (in_block, 1)]
             = [(2, 8704), (272, 32), (8, 17408), (32, 1)]     # 2*272*8*32 = 139,264

BD_MAX_SIZE = 512: the BD size field is 10 bits, but bf16 folds two elements into a 32-bit word, so the real per-dimension ceiling is 512 elements. _split_bd_size(n) factors n and prefers the smallest hi.

Replay BD

aie.dma_bd_packet(0, proj_x_pkt_id.from_replay)          # every replay channel shares this id
dimensions = [(x_dim // 256, 256), (L_TOKENS, x_dim), (256, 1)]
# emits x_dim/256 slices, each L_TOKENS × 256 = 2048 bf16 = one x_slice_ty
Why every replay channel shares one id. x reaches the 16 cores on a circuit flow, so no id is needed at the cores. The only merge left is inside MT[2]'s own FIFO. If each width had a distinct id, each would be its own packet flow, the pathfinder would grow a separate multicast tree per id, the trees would diverge, and the arbiter allocator would tie one master port to two arbiters — which AIEDialect.cpp:2047 rejects. One id, one port, one tree per hop.
Why the x FIFO is on MT[1] and not MT[2]. The pathfinder cannot route a zero-hop packet flow — source and destination on the same switchbox leaves the destination port unset, and the rule comes out on South : 0. So the FIFO that turns the replay stream into the circuit broadcast has to sit one hop away, on MT[1].

9.1 The row-block permutation (engine output)

One engine round is 16 cores × L tokens × 32 rows = 4096 values, laid out row-block major:

The qkv rows are the exception: they reach the RoPE tile still permuted — see §15.

9.2 The up|gate weave

The host interleaves the up and gate weight matrices in blocks of WEAVE = 512 rows so that the engine's 68 rounds arrive as alternating up/gate pairs and the GLU tile never has to buffer more than four rounds:

woven row index for logical index i:
    (i / WEAVE) * 2 * WEAVE  +  i % WEAVE          // up
    (i / WEAVE) * 2 * WEAVE  +  WEAVE + i % WEAVE  // gate

host load: blocks     = 1024 / 2 / 32 * (D / 256)
           chunk_size = blocks * q4k_bytes(32 * 256)
           for i: reorder_cpy(w_up_tensor[i]) ; reorder_cpy(w_gate_tensor[i])

The CPU golden model applies exactly the same index arithmetic when computing silu(g)·u, so any weave mismatch shows up as a comparison failure rather than silent drift.

9.3 reorder_cpy — the vertical-block interleave

reorder_cpy(dst, src, col, vertical_blocks = 2) alternates whole q4k_bytes(32·256)-sized blocks between two row blocks, so that a memtile's contiguous w_buffer[0 : 2·W_BLOCK_SIZE] splits correctly into the two blocks its two consumer BDs expect.

9.5 The 16-word y header

Every combo's y buffer is 16 + L·m·2 = 528 elements. The kernel writes the routing packet id at y[14]; the payload starts at y[16]. The MM2S BD is aie.dma_bd(y_buffer, offset = 14, len = 2·m_chunk + 2) — 2 header elements (one 32-bit word) plus 512 payload. The rms tile uses the identical convention: aie.dma_bd(self.y, offset = 14, len = D + 2) on a (D+16,) buffer.

12.2 bf16 rounding, and why the golden model mirrors it

aie::accum::to_vector<bf16>() truncates toward −inf on every fp32→bf16 narrowing inside a kernel. host.cpp's CPU chain therefore calls round_bf16() at exactly the same points — after the input norm, after each projection, after the per-head norms, after RoPE, after the softmax, after the gate, after each residual add, and after SwiGLU — so that a comparison failure means a real dataflow bug rather than accumulated rounding.

 1  rtp_write(attn_qk_tiles[i], l_qk_address, L)   for both CUs
 2  rtp_write(attn_kv_tiles[i], l_kv_address, L)   for both CUs
 3  _send_hidden_states()
 4  _send_rms_weights()
 5  _send_rope_rms_weights()
 6  _receive_kv_cache()
 7  _receive_layer_out()
 8  _move_weights(qkv)
 9  _move_weights(z)
10  npu_dma_wait(attn_tile, S2MM, ch0)          # cache append complete
11  _move_kv_cache()                            # read the cache back in
12  _move_weights(o    : D, DQ)
13  _move_weights(up|gate : 2I, D)
14  _move_weights(down : D, I)
15  npu_dma_wait(xyr_tile, S2MM, ch1)           # h2 landed
Three ordering rules, documented in decoding_layer.cpp:
  1. Weight moves and mvm calls are paired positionally — the n-th _move_weights feeds the n-th mvm() in proj_main.cc. Reordering either side silently mismatches them.
  2. Every read (_receive_*) must be posted before any weight moves, or the array stalls with nowhere to drain.
  3. _send_rope_rms_weights() must not wait for completion — inserting a wait there deadlocks the pass.

14 · Why it is shaped this way

14.1 One-hot packet ids in the y tree

Every id in the engine's y tree is the only one with its bit set, so the mask that splits it off a shared slave port is that bit alone and cannot match the others. Give two of them a shared bit and the rule generator either lets one swallow the other (mask widening produces a false match) or refuses the port outright. to_glu = 16 is one-hot on purpose: a widened mask that admits it cannot admit another id in the tree.

14.2 Two masksets per master port

A master port carries at most two destination sets. rms_core.Y_out emits three ids, but only two destinations: both norms land on the same MT[2] port (told apart by arrival order, not by id), so AIECreatePacketFlows merges to_proj and to_st into one group, and the port ends up with exactly two masksets — west to MT[2], south to the shim. A third set off this port would not route, whatever the id or destination: the allocator ties the port to two arbiters and AIEDialect.cpp:2047 rejects it.

Consequence: the post-attention norm has no DDR tap of its own. If you want to observe h1 or the phase-2 output, you have to free a maskset first.

14.3 No zero-hop packet flows

The pathfinder cannot route a packet flow whose source and destination are the same switchbox — the destination port is left unset and the rule emerges on South : 0. This is why MT[2]'s replay output has to travel one column west to MT[1]'s FIFO before it can be broadcast.

14.5 bf16 in aie::mmul

mmul<8,8,8,bf16> on npu2 floors both operands onto a shared-exponent-per-8 grid (effectively bfp16). Where accuracy matters, weights are pre-rounded on the host and the dequant path uses two-limb bf16 splitting. This is why q4_core.h reduces integer sums first and applies the bf16 super-block scale afterwards.

15 · Known gaps & documentation drift

15.1 The L = 8 attention gaps

#WhereProblem
1iron/attn.py :: qk_tile attn_q_ty = (8·256,) = 2048 elements — one token's padded head group — and the landing BD is 2048 long. But RoPE.Q_out sends DQ/2 = 3072 per CU per token. 3072 is not a multiple of 2048, so the q chain cannot be satisfied as written.
2iron/RoPE.py q_buffer is PADDED_DQ = 8192, but MM2S0 only emits the first DQ = 6144 elements (two 3072 halves). The 2048 padding elements are never sent, so the padded-head layout the CUs expect is not what leaves the tile.
3kernels/attn_qk.cc aie::mask<16> mask = aie::le(idx, (i < 16) ? i : 16) is a length mask (it trims the final partial KV chunk), not a causal mask. At L = 8 every query row would attend to the full cache. The L RTP is likewise the KV length (rounds = (L[0]+15)/16), not the query count.
4kernels/attn_qk.cc The outer for (int h = 0; h < 6; h++) trip count is hardcoded and does not derive from any of ATTN_ROUNDS (4), KV_HEADS_PER_CU (1) or L_TOKENS (8).
5iron/RoPE.py The qkv rows arrive from the engine row-block permuted (§9.1). Every other consumer un-permutes in its landing BD; the RoPE tile does not, so it sees raw[(rb·L + t)·32 + r] rather than token-major rows.
6iron/aux_memtile.py Docstring notes that multi-dimensional memtile BDs beyond 3 dims are unverified in this IRON version. MT[2]'s down landing BD uses 4 dims.
